## 1. الغرض من الوثيقة

توثق هذه الوثيقة التصميم المتفق عليه لإنشاء منظومة موحدة لا يكون فيها البوت ولوحة التحكم نظامين منفصلين، وإنما قناتين لعرض وتشغيل محرك أعمال واحد وعقود صلاحيات واحدة.

النتيجة المطلوبة هي:

1. تسجيل الدخول إلى لوحة التحكم حصراً من داخل البوت.
2. إلغاء صفحة ومنهجيات تسجيل الدخول القديمة بالكامل.
3. تشغيل الرابط المحلي ورابط النفق في الوقت نفسه.
4. قصر دخول لوحة التحكم على السوبر أدمن والجينرال أدمن ومشرف الموقع.
5. جعل وظائف وبيانات وصلاحيات لوحة التحكم انعكاساً كاملاً لوظائف البوت.
6. تطبيق صلاحيات موحدة على الواجهة والخادم والحقول والاستعلامات والتصدير.
7. إضافة رتبة العامل المشرف بتفويضات دقيقة على مستوى الوظيفة داخل الموديول.
8. إنشاء واجهات وتحليلات احترافية مناسبة للمتصفح لكل وظيفة.
9. إلزام كل وظيفة مستقبلية بالتنفيذ في البوت ثم لوحة التحكم قبل اعتبار دورة توثيقها مكتملة.
10. ربط جميع الأخطاء والحوادث بعقد الرصد الموحد في PLAN-20.

هذه الوثيقة لا تمنح إذناً لبدء تعديل الكود. يبدأ التنفيذ فقط بعد اعتماد الوثيقة كتابياً، وإنشاء PLAN-21 التفصيلية ومراجعتها.

## 3. المبادئ المعمارية الحاكمة

### 3.1 محرك أعمال واحد

البوت والداشبورد محولات عرض وتشغيل لقواعد أعمال مشتركة. يمنع تكرار الحسابات أو قواعد التحقق أو منطق الاعتمادات داخل كل واجهة بصورة مستقلة.

### 3.2 عقد وظيفة واحد

كل وظيفة تملك عقداً مركزياً يحدد اسمها وصلاحياتها ومدخلاتها ومخرجاتها وحالاتها ونطاقها وحقولها وقنواتها وتحليلاتها.

### 3.3 المنع الافتراضي

أي دور أو وظيفة أو إجراء أو حقل أو نطاق غير معرف صراحة يعامل كـ DENY.

### 3.4 الصلاحيات على الخادم

إخفاء الأزرار والقوائم مطلوب لتحسين تجربة الاستخدام، لكنه ليس حماية أمنية كافية. يجب إعادة فحص الصلاحية في مسار الخادم قبل القراءة أو الكتابة أو التصدير.

### 3.5 عدم إرسال البيانات المحجوبة

الحقول الحساسة لا ترسل إلى المتصفح أو Telegram ثم تخفى بصرياً؛ تستبعد من الاستعلام أو من طبقة الإسقاط الآمن قبل تكوين الاستجابة.

### 3.6 التطابق الوظيفي مع اختلاف العرض

تتطابق الأسماء والحقول والحسابات والحالات والصلاحيات والنتائج بين البوت والداشبورد. يسمح للداشبورد بعرض أكثر ملاءمة للمتصفح دون تغيير قواعد الوظيفة.

### 3.7 التتبع الكامل

كل إجراء مصادقة أو تفويض أو تغيير صلاحية أو تعديل مالي أو محاولة وصول مرفوضة يسجل بعقد التدقيق والحوادث الموحد، دون تخزين الأسرار أو البيانات الشخصية الخام.

## 6. قواعد إدارة الأدوار

### 6.1 السوبر أدمن

- يستطيع تعيين وإدارة جميع الأدوار.
- يمنع حذف أو تعطيل أو خفض رتبة آخر سوبر أدمن فعال.
- يستطيع إنهاء جلسات أي مستخدم.
- يملك وحده صلاحيات النظام السيادية المحددة في قسم الوظائف غير القابلة للتفويض.

### 6.2 الجينرال أدمن

- يستطيع إدارة FIELD_ADMIN وWORKER_SUPERVISOR وWORKER وSUPPLIER وGUEST.
- لا يستطيع إنشاء أو تعديل أو خفض SUPER_ADMIN أو GENERAL_ADMIN.
- لا يستطيع منح صلاحيات تقنية أو سيادية.

### 6.3 مشرف الموقع

- لا يستطيع تغيير الأدوار.
- يستطيع تقديم طلب تعيين عامل مشرف داخل موقعه المسجل.
- لا يستطيع اعتماد طلب التفويض الذي أنشأه.

### 6.4 الأدوار الأخرى

لا تملك أي صلاحية لإدارة الأدوار أو منح التفويضات.

## 7. نموذج الصلاحيات المركزي

### 7.1 مكونات القرار

قرار السماح لا يعتمد على الدور وحده، بل على:

~~~text
AccessDecision =
  Role
  + PermissionKey
  + Action
  + DataScope
  + FieldPolicy
  + AccountStatus
  + SiteAssignment
  + DelegationState
  + ChannelPolicy
~~~

### 7.2 الإجراءات القياسية

- view
- create
- submit
- edit
- withdraw
- approve
- reject
- settle
- export
- print
- manage

لا تعني صلاحية view امتلاك create أو edit. كل إجراء يصرح به مستقلاً.

### 7.3 النطاقات القياسية

| النطاق | الوصف |
|---|---|
| self | بيانات المستخدم أو العامل أو المورد نفسه. |
| assigned-site | الموقع المسجل للمستخدم فقط. |
| assigned-resource | مخزن أو عهدة أو معدة محددة داخل الموقع المسجل. |
| all-sites | جميع المواقع، ويمنح للأدوار العليا وفق الوظيفة. |
| system | إعدادات أو بيانات سيادية على مستوى النظام. |

### 7.4 صيغة الإذن

تستخدم مفاتيح ثابتة قابلة للاختبار، مثل:

~~~text
workforce.worker.view
workforce.compensation.view
workforce.compensation.edit
advances.cash.create
advances.withdrawals.view
custody.settlement.create
inventory.kitchen.issue.create
inventory.fuel.level.create
requests.bonus.submit
requests.bonus.approve
reports.feature.export
system.roles.manage
~~~

### 7.5 مواضع تطبيق القرار

يطبق القرار نفسه في:

1. قائمة أوامر Telegram.
2. القائمة الرئيسية.
3. أزرار الموديول والوظيفة.
4. معالج Callback أو الرسالة.
5. خدمة الأعمال.
6. مستودع البيانات والاستعلام.
7. صفحات الداشبورد والقائمة الجانبية.
8. مسارات API.
9. التصدير والطباعة.
10. الإحصائيات والرسوم.
11. المرفقات.

## 8. مصفوفة دخول لوحة التحكم

| الدور | دخول الداشبورد | النطاق |
|---|:---:|---|
| SUPER_ADMIN | نعم | حسب صلاحيات السوبر أدمن، وجميع المواقع عند سماح الوظيفة. |
| GENERAL_ADMIN | نعم | جميع المواقع والوظائف التشغيلية المسموحة، دون السيادية. |
| FIELD_ADMIN | نعم | الموقع المسجل فقط مع حجب المستحقات التعاقدية. |

| WORKER | لا | البوت فقط. |

وجود وظيفة عامل أو مورد أو زائر في عقد التطابق لا يمنح هذه الأدوار دخول الداشبورد. تعرض لوحة التحكم الجانب الإداري أو الرقابي أو التشغيلي من بيانات الوظيفة فقط للأدوار الثلاثة المخولة وبحسب أذوناتها. ولا ينشأ إجراء باسم المستخدم أو نيابة عنه ما لم يكن الإجراء نفسه مسموحاً للدور في عقد الوظيفة.

## 9. رتبة العامل المشرف

### 9.1 الطبيعة

WORKER_SUPERVISOR عامل معتمد يحتفظ بجميع صلاحيات WORKER الذاتية ويضاف إليه تفويض أو أكثر على مستوى وظيفة دقيقة.

### 9.2 التحويل التلقائي

- عند اعتماد أول تفويض فعال يتحول العامل تلقائياً من WORKER إلى WORKER_SUPERVISOR.
- عند سحب أو انتهاء آخر تفويض يعود تلقائياً إلى WORKER.
- يمنع وجود WORKER_SUPERVISOR بلا تفويض فعال.

### 9.3 تعدد التفويضات

يجوز منح العامل المشرف عدة وظائف دقيقة مستقلة. لكل تفويض دورة حياة منفصلة، ويمكن إيقافه أو سحبه دون التأثير في بقية التفويضات.

### 9.4 مستوى التفويض

التفويض يكون لوظيفة داخل الموديول، وليس للموديول كاملاً.

أمثلة:

- inventory.fuel.level.create يسمح بتسجيل منسوب السولار فقط.
- inventory.kitchen.issue.create يسمح بصرف صنف من مخزن المطبخ فقط.

لا يسمح المثال الأول بإدارة التنكات أو تعديل التاريخ أو التصدير، ولا يسمح المثال الثاني بالتوريد أو الجرد أو الاطلاع على تقارير غير مصرح بها.

### 9.5 النطاق

- يرتبط التفويض بالموقع المسجل فعلياً على العامل.
- لا يمكن اختيار موقع مختلف.
- لا يمنح العامل المشرف نطاق all-sites.
- عند نقل العامل إلى موقع آخر توقف جميع تفويضاته تلقائياً حتى يعاد اعتمادها للموقع الجديد.

### 9.6 الجهة المخولة

- SUPER_ADMIN وGENERAL_ADMIN: منح وتعديل وإيقاف وسحب التفويض.
- FIELD_ADMIN: تقديم طلب تفويض لعامل داخل موقعه فقط.

### 9.7 المدة

- تاريخ البداية إلزامي.
- تاريخ النهاية اختياري.
- يستمر التفويض حتى السحب إذا لم يحدد تاريخ نهاية.
- يوقف تلقائياً عند إيقاف العامل أو إنهاء خدمته أو نقله.

### 9.8 بيانات سجل التفويض

- المستخدم والعامل المرتبط.
- FlowCode.
- PermissionKey والإجراءات المسموحة.
- الموقع والمورد التشغيلي المحدد إن وجد.
- تاريخ البداية والنهاية.
- مقدم الطلب.
- المعتمد.
- سبب المنح.
- الحالة.
- تاريخ الإيقاف أو السحب وسببه.
- سجل الاستخدام ومحاولات الرفض.

### 9.9 الوظائف غير القابلة للتفويض

يحظر تفويض:

- إدارة المستخدمين والأدوار والصلاحيات.
- عرض أو تعديل المستحقات التعاقدية لعمال آخرين.
- تعديل الراتب الأساسي أو الإضافي أو البدلات.
- إعدادات النظام والخوادم.
- خزنة الأخطاء والتدقيق الأمني.
- المحاكاة ووضع الشبح.
- النسخ الاحتياطية والاستعادة.
- إنشاء أو تعديل SUPER_ADMIN أو GENERAL_ADMIN.
- الاعتمادات المالية النهائية الحساسة.
- أي وظيفة يحمل عقدها delegatable: false.

## 10. سرية المستحقات التعاقدية

### 10.1 التعريف

المستحقات التعاقدية السرية للعامل تشمل:

- الراتب الأساسي.
- الراتب الإضافي.
- البدلات الثابتة أو الدورية المسجلة للعامل.
- إجمالي المستحقات التعاقدية المشتق من هذه القيم.
- أي إحصائية أو تقرير أو تصدير يكشف القيم السابقة مباشرة أو يسمح باستنتاجها.

لا تدخل السلف والمسحوبات النقدية أو العينية في هذا التعريف.

### 10.2 مصفوفة الوصول

| الدور | عرض المستحقات التعاقدية | تعديلها | تشغيل المسير أو الاعتماد |
|---|:---:|:---:|:---:|
| SUPER_ADMIN | نعم | نعم | نعم |
| GENERAL_ADMIN | نعم | لا | نعم وفق الوظيفة |
| FIELD_ADMIN | لا | لا | لا |
| WORKER_SUPERVISOR | بياناته الشخصية في قسيمته فقط | لا | لا |
| WORKER | بياناته الشخصية في قسيمته فقط | لا | لا |
| SUPPLIER | لا | لا | لا |
| GUEST | لا | لا | لا |

### 10.3 الحجب الفني

- تمنع الحقول في الاستعلام أو طبقة الإسقاط.
- تمنع في API وصفحات التفاصيل والجداول.
- تمنع في البحث والفرز والتصفية والاقتراح التلقائي.
- تمنع في Excel وPDF وCSV والطباعة.
- تمنع في بطاقات المؤشرات والرسوم وإجماليات الموقع.
- تمنع في السجلات والرسائل والإشعارات.
- لا تستخدم قيم رواتب خاماً في أخطاء يمكن أن تظهر لمشرف الموقع.

### 10.4 السلف والمسحوبات والعهد

FIELD_ADMIN يستطيع داخل موقعه:

- تسجيل السلف النقدية.
- تسجيل المسحوبات العينية.
- عرض سجلات السلف والمسحوبات.
- تسجيل العهد وتشغيلها وتغذيتها.
- تسجيل مصروفات العهد.
- إجراء تصفية العهد كاملة.

تنفذ هذه العمليات دون كشف الراتب أو البدلات أو صافي المستحقات.

## 11. طلبات المكافآت والخصومات والجزاءات

### 11.1 صلاحيات مشرف الموقع

- إنشاء طلب مكافأة أو خصم أو جزاء داخل موقعه.
- إرفاق السبب والمبلغ والمستندات المطلوبة.
- متابعة حالة الطلب.
- سحب الطلب ما دام PENDING ولم تبدأ مراجعته.
- لا يستطيع إنشاء قيد مالي نهائي.
- لا يستطيع تعديل الطلب بعد الإرسال.
- لا يستطيع الاعتماد أو الرفض.
- لا يرى أثر الطلب على صافي الراتب.

### 11.2 صلاحيات الجينرال أدمن

- مشاهدة الطلبات وحالاتها للمتابعة الإدارية.
- لا يستطيع تعديلها أو اعتمادها أو رفضها.

### 11.3 صلاحيات السوبر أدمن

- بدء المراجعة.
- تعديل الطلب مع تسجيل الفرق والسبب.
- الاعتماد أو الرفض.
- إنشاء الأثر المالي النهائي عند الاعتماد.

### 11.4 دورة الحالة

~~~text
DRAFT
  -> PENDING
  -> UNDER_REVIEW
  -> APPROVED
  -> REJECTED

PENDING
  -> WITHDRAWN
~~~

- لا يحذف الطلب المسحوب.
- يمنع السحب بعد UNDER_REVIEW.
- لا يؤثر الطلب في حساب العامل قبل APPROVED.
- يحتفظ القيد النهائي بهوية مقدم الطلب وهوية السوبر أدمن المعتمد.

## 13. منهجية تنفيذ وترحيل كل وظيفة

يطبق التسلسل التالي على كل وظيفة منفردة:

1. فحص الوظيفة في F:\HR وتوثيق خطواتها وقواعدها وشيتاتها وصلاحياتها.
2. فحص عقود ووثائق المشروع الحالي ومكونات packages المشتركة.
3. إنشاء أو استكمال عقد الوظيفة الموحد.
4. تنفيذ الوظيفة في موديول البوت بالكامل.
5. تشغيل اختبارات البوت والبيانات والصلاحيات والحوكمة.
6. تفعيل وظيفة البوت طبيعياً فور اكتمالها؛ لا تستخدم Feature Flags غير لازمة.
7. بدء واجهة الداشبورد لنفس الوظيفة مباشرة.
8. استخدام خدمات الأعمال نفسها في القناتين.
9. إضافة العرض والتحليلات والميزة الاحترافية المناسبة للمتصفح.
10. تشغيل اختبارات التطابق بين البوت والداشبورد.
11. تحديث الوثائق وسجل الترحيل.

حالات المتابعة:

~~~text
LEGACY_AUDITED
BOT_IN_PROGRESS
BOT_VERIFIED
DASHBOARD_IN_PROGRESS
PARITY_VERIFIED
COMPLETE
~~~

وجود BOT_VERIFIED يسمح باستخدام الوظيفة في البوت، لكنه لا يسمح بتسجيل حالة COMPLETE في سجل التطابق حتى اكتمال الداشبورد.

### 13.1 الوظائف الحالية

بعد استقرار المصادقة والصلاحيات المركزية تكون الأولوية لإنشاء نسخ الداشبورد لجميع وظائف البوت الحالية قبل استكمال وظائف جديدة.

إذا كانت وظيفة حالية في البوت غير مطابقة للمرجع أو لا تستخدم العقد المشترك، تصلح في البوت أولاً ثم تنقل إلى الداشبورد.

### 13.2 الوظائف المستقبلية

لا تعتبر وظيفة جديدة مكتملة توثيقياً إلا بعد:

- تنفيذها واختبارها في البوت.
- تنفيذها واختبارها في الداشبورد.
- إضافة تحليلها الاحترافي.
- اجتياز اختبار التطابق.
- تحديث docs/19.

- مؤشرات مختصرة.
- الأعمال المطلوبة اليوم.
- الطلبات المعلقة التي يملك المستخدم إجراءً عليها.
- التنبيهات والحالات الشاذة.
- آخر العمليات.
- اختصارات الوظائف الأكثر استخداماً.
- رابط مركز الإحصائيات.

### 14.3 الهيكل الهجين

- مركز رئيسي لكل موديول.
- صفحة أو تبويب مستقل لكل وظيفة.
- ملخص إحصائي صغير داخل صفحة الوظيفة.
- زر فتح التحليل الكامل.
- لا توضع عشرات الوظائف مباشرة في القائمة الجانبية.

- فلاتر إضافية خاصة بالوظيفة.

### 15.2 محتوى التحليل

- بطاقات KPIs.
- إحصائيات اليوم والشهر والفترة.

- الحالات الشاذة والتنبيهات.
- أحدث العمليات والتعديلات.

### 15.5 سلامة البيانات

- تحسب المقاييس على الخادم.
- لا ترسل بيانات خاماً محجوبة بغرض حسابها في المتصفح.
- لا تعرض بيانات وهمية عند غياب البيانات.
- تعرض حالة فارغة واضحة.
- يوثق تعريف ومعادلة كل KPI ومصدره.

## 18. تسجيل الدخول الجديد من البوت فقط

### 18.1 القاعدة

لا توجد صفحة Login ولا طريقة دخول من الويب.

الدخول الوحيد:

1. يفتح المستخدم إعدادات البوت.
2. يتحقق البوت من الحساب وحالته ودوره.
3. يظهر زر الرابط المحلي وزر رابط النفق للأدوار الثلاثة المخولة.
4. ينشئ البوت رمزاً عشوائياً منفصلاً لكل رابط.
5. يضغط المستخدم الرابط.
6. يتحقق خادم الداشبورد من الرمز ويستهلكه ذرياً لمرة واحدة.
7. يعيد الخادم قراءة الحساب والدور والموقع.
8. ينشئ جلسة خادم آمنة.
9. ينتقل المستخدم مباشرة إلى /admin.

### 18.2 شاشة الإعدادات

- SUPER_ADMIN يرى الإعدادات الكاملة وقسم لوحة التحكم والجلسات.
- GENERAL_ADMIN وFIELD_ADMIN يريان شاشة محدودة للحساب ولوحة التحكم والجلسات.
- لا يؤدي تمكينهما من فتح لوحة التحكم إلى كشف إعدادات السوبر أدمن.

### 18.3 مسارات العودة

- فتح /admin بلا جلسة يعيد إلى رابط البوت العميق.
- الرمز المنتهي أو المستخدم أو غير الصالح يعيد إلى البوت.
- المستخدم غير المصرح له يعاد إلى البوت وتُسجل محاولة الرفض.
- تسجيل الخروج يعيد إلى البوت.

رابط العودة:

~~~text
https://t.me/<BOT_USERNAME>?start=dashboard_access
~~~

لا توجد صفحة ويب بديلة لتسجيل الدخول.

## 19. الرابط المحلي ورابط النفق معاً

### 19.1 متغيرات البيئة

~~~env
DASHBOARD_LOCAL_URL=http://localhost:3002
DASHBOARD_TUNNEL_URL=https://your-tunnel-domain.example
TELEGRAM_BOT_USERNAME=your_bot_username
DASHBOARD_AUTH_LINK_SECRET=<secret>
DASHBOARD_AUTH_LINK_TTL_MINUTES=5
DASHBOARD_SESSION_TTL_HOURS=8
DASHBOARD_SESSION_NOTICE_MINUTES=60
DASHBOARD_SESSION_EXTENSION_HOURS=8
~~~

الأسماء محايدة عن ngrok، ويقبل DASHBOARD_TUNNEL_URL رابط ngrok أو Cloudflare Tunnel أو نطاق HTTPS آخر.

### 19.2 العمل المتزامن

- الرابطان يعملان في الوقت نفسه.
- تعطل النفق لا يوقف localhost.
- تعطل localhost لا يوقف النفق.
- تغيير رابط النفق يتم من ملف البيئة دون تعديل الكود.
- لا يوجد تحويل تلقائي بين الرابطين.

### 19.3 أزرار البوت

- فتح لوحة التحكم محلياً.
- فتح لوحة التحكم عبر النفق.

ينشأ لكل زر رمز مستقل حتى لا يؤدي استخدام أحدهما إلى إبطال الآخر.

### 19.4 قيود localhost

localhost يعمل على الجهاز الذي يشغل الداشبورد فقط. الهاتف أو جهاز آخر يستخدم رابط النفق.

### 19.5 حماية المضيف والتحويل

- تخزن قائمة المصدرين الموثوقين في الإعدادات.
- يرفض أي Host أو Origin ثالث.
- لا يعتمد التحويل على req.url أو Host Header غير موثوق.
- يربط الرمز بنوع الهدف local أو tunnel.
- يبنى redirect من القيمة الموثقة في الإعدادات.

### 19.6 Cookies

- HttpOnly دائماً.
- SameSite=Lax.
- Secure لرابط HTTPS.
- إعداد محلي مناسب لـ localhost فقط.
- لا تستخدم Domain واسعة.
- الجلسة المحلية وجلسة النفق مستقلتان في المتصفح.

## 20. رمز الدخول أحادي الاستخدام

### 20.1 الخصائص

- عشوائية تشفيرية قوية.
- مدة خمس دقائق.
- استخدام واحد.

- already_used
- invalid_signature
- unknown_user
- inactive_user
- unauthorized_role
- target_origin_mismatch
- role_changed
- site_assignment_invalid

## 21. جلسات لوحة التحكم

### 21.1 السياسة

- مدة الجلسة الأساسية ثماني ساعات.
- يسمح بجلسة localhost وجلسة tunnel في الوقت نفسه.
- لا يوجد خيار تذكرني طويل المدة.
- لا تخزن Session ID أو JWT في localStorage أو sessionStorage.
- تكون قاعدة البيانات هي مرجع حالة الجلسة.

### 21.2 التحقق عند كل طلب

- الجلسة موجودة.
- غير منتهية.
- غير مسحوبة.
- الحساب فعال.
- الدور الحالي يسمح بالداشبورد.
- الموقع صالح.
- نسخة الصلاحيات لم تتغير.
- المسار والإجراء مسموحان.

### 21.3 الإبطال الفوري

تبطل جميع الجلسات عند:

- تغيير الدور.
- تغيير الموقع.
- إيقاف الحساب.
- إنهاء الخدمة.
- سحب صلاحية الداشبورد.
- إنهاء جميع الجلسات من البوت.

### 21.4 بيانات الجلسة الخادمية

- Session ID Hash.
- User ID وTelegram ID.
- Origin Kind: LOCAL أو TUNNEL.
- وصف مختصر للمتصفح والجهاز.
- User-Agent Hash اختياري للتحقق والتنبيه.
- وقت الإنشاء.
- آخر نشاط.
- وقت الانتهاء.
- وقت إرسال تنبيه الانتهاء.
- وقت التمديد.
- وقت الإبطال وسببه.
- معرف رمز الدخول المنشئ.
- traceId.

لا يخزن IP خاماً في السجلات طويلة الأمد. إذا استخدم لكشف إساءة الاستخدام يحجب أو يختصر وفق سياسة الخصوصية.

## 22. إشعار انتهاء الجلسة وتمديدها

### 22.1 الإشعار

قبل انتهاء الجلسة بساعة يرسل البوت إشعاراً يحتوي:

- نوع الجلسة: محلية أو نفق.
- الجهاز والمتصفح بشكل مختصر.
- آخر نشاط.
- وقت الانتهاء.
- زر تمديد ثماني ساعات.
- زر إنهاء الجلسة.
- زر إدارة جميع الجلسات.

### 22.2 التمديد

- زر التمديد مملوك لنفس Telegram ID.
- يعاد فحص الحساب والدور والموقع والصلاحيات.
- تضاف ثماني ساعات بعد تأكيد Telegram.
- يسجل التمديد كتأكيد هوية جديد.
- يعاد ضبط موعد إشعار الانتهاء.
- يبطل زر الإشعار القديم بعد الاستخدام.

### 22.3 عدم الاستجابة

## 40. معايير اكتمال التوثيق قبل التنفيذ

لا تبدأ PLAN-21 التنفيذية قبل تحقق ما يلي:

- مراجعة المستخدم لهذه الوثيقة.
- عدم وجود قرار معماري معلق.
- عدم وجود TBD أو Placeholder.
- إنشاء جرد الوظائف الكامل في PLAN-21.
- ربط كل مهمة بملفات واختبارات وأمر تحقق.
- تحديد قائمة الحذف بعد Reference Audit.
- تحديد حدود التعديل في packages المشتركة.
- تحديد ترتيب الموديولات بناء على الاعتماديات.
- توثيق خطة مهاجرات غير مدمرة وخطة رجوع.
- توثيق بوابات الاختبار والبناء والحوكمة.

## 41. الخلاصة المعمارية

النظام المستهدف يعتمد على:

- سبعة أدوار فقط.
- ثلاث رتب فقط تدخل الداشبورد.
- عقد صلاحيات ووظائف مركزي.
- تنفيذ البوت أولاً ثم الداشبورد لكل وظيفة.
- تطابق كامل في قواعد الأعمال والصلاحيات والبيانات.
- حجب خادمي للمستحقات التعاقدية.
- تفويض عامل مشرف على مستوى الوظيفة والإجراء والموقع.
- دخول أحادي الاستخدام من البوت.
- رابط محلي ونفق متزامنان.
- جلسات خادمية قابلة للتمديد والإبطال من Telegram.
- صفحة ملخص حسب الدور.
- مركز إحصائيات موحد.
- تحليل وميزة متصفح احترافية لكل وظيفة.
- تسجيل أخطاء وتدقيق موحدان وفق PLAN-20.

لا توجد في هذا التصميم طريقة دخول ويب مستقلة، أو دور غير معتمد، أو صلاحية موديول عامة للعامل المشرف، أو استثناء يسمح لمشرف الموقع برؤية المستحقات التعاقدية.
