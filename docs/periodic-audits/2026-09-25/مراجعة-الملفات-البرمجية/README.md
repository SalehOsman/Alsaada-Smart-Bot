# فحص ساكن للملفات البرمجية — 2026-09-25

## النطاق والمنهج
جردت ملفات المصدر الشبيهة بـTypeScript/JavaScript في `apps/`, `packages/`, `modules/`, و`tools/`؛ نتج 652 ملفًا تقريبًا بعد استبعاد أسماء ملفات الاختبارات من العد. أجريت قراءة موجهة لمداخل التشغيل، عقد الموديولات، ربط المسارات، مخطط Prisma ومستودعات مختارة، الإعدادات وDocker/CI، إلى جانب searches ساكنة عن `tenantId`, نقاط HTTP/polling، واستعلامات tenant.

هذه مراجعة مخاطر موجهة وليست قراءة سطرية موثقة لكل ملف من الملفات الـ652، ولا SAST مثبتًا أو تحققًا تشغيليًا. لم أشغل اختبارات أو بناء أو اتصالًا بقاعدة بيانات، ولم أقرأ ملفات الأسرار المحلية.

## الحكم
المشروع مبني فعليًا كبنية موديولية كبيرة وموجهة لأعمال شركة السعادة، وليس قالب بوت عام جاهزًا للنسخ. يوجد فاصل packages/modules وباص موديولات، لكن بعض الحدود لا تزال رخوة، وداخل bot-server مسارات مباشرة للرواتب والسلف والموردين، فيما نموذج Tenant جزئي بلا سياق تشغيل ثابت. يلزم حسم الشركة الواحدة/التعدد قبل استخدامه أساسًا لـTembot.

## نتائج الشيفرة

### C1 — P1: لا يوجد tenant context موحد ولا ضمان scoping لكل الاستعلامات
- `packages/core-components/src/contracts/module.contract.ts`: `ModuleRuntimeContext` يحوي Prisma/Redis/API ولا يحوي معرف شركة/tenant؛ كما يسمح بخصائص مفتوحة `any`.
- `packages/database/prisma/schema.prisma`: `Tenant` موجود؛ `tenantId` مطلوب في بعض السجلات واختياري في أخرى. `User.telegramId` فريد عالميًا و`User.tenantId` nullable.
- مستودعات `settings` و`workforce` و`system-data.service` تبحث عن `tenant.findFirst()` دون محدد ثابت، وبعض عمليات ملف الشركة تستخدم `companyProfile.findFirst()`.

الأثر: النموذج لا يحقق عزلًا متعدد الشركات على مستوى السياق والاستعلامات. إذا كان النظام سيبقى لشركة واحدة، فهي بقايا تزيد الالتباس؛ وإذا صار مشتركًا، فهي فجوة عزل ذات أولوية.

### C2 — P1: bot-server يجمع النواة ومسارات أعمال الشركة مباشرة
`apps/bot-server/src/bot.ts` طوله 749 سطرًا. حول Module Bus ما زالت هناك أوامر ومطابقات نصية وقراءات مباشرة من Prisma تخص قسيمة الراتب، كشف السلف/المسحوبات، بوابة الموردين، وتسجيل منسوب الموقع (نحو الأسطر 563–660). توجد أيضًا جسور إلى handlers داخل `settings` و`workforce` مع casts مثل `as any`. هذا يثبت أن إزالة وظائف الشركة تحتاج فصل مسارات/خدمات المجال، لا نسخ ملفات النواة وحدها.

### C3 — P1: عقد الموديول لا يفرض حدود الخدمات بوضوح
`ModuleRuntimeContext` يصرح بـ`redis: any` و`telemetry?: any` و`[key: string]: any`، ويستخدم `options?: any` بعقود الموديول. يتعارض ذلك مع وصف strict/Zero-any في ADR-003 ووثائق الحوكمة، ويضعف كشف أخطاء الربط عند تحويل المشروع إلى قالب قابل للامتداد.

### C4 — P1: أوامر التهيئة المعلنة لا تقابل أداة موجودة
الجذر يحتوي `system:provision` لكنه يشير إلى `scripts/provision.ts` غير الموجود. `tenant:init` في docs لا يظهر ضمن scripts. يوجد `@alsaada/database db:seed:company` و`db:migrate`، لكنهما لا يطابقان دليل التهيئة متعدد الخيارات الموصوف في docs/06.

### C5 — P1 مشروط بالنشر: كلمات مرور Compose افتراضية معروفة
`docker-compose.yml` يضع قيم fallback ثابتة لكلمة مرور PostgreSQL وRedis. إذا شغّل المشغل compose دون overrides صريحة، تصبح القيم قابلة للتخمين. لا يفحص هذا التقرير إعداد بيئة بعينها ولا يقرأ ملف `.env`.

### C6 — P2: نقطة health تعطي `ready` دون فحص صحة الـrunner
`apps/bot-server/src/index.ts` يشغل grammY runner عبر polling، ثم يقدم نقطة `/api/health` من `node:http` وتعيد `status: ready`. لا يظهر في handler استعلام لصحة runner بعد بدء الخدمة أو مؤشر فشل polling. وفي `docker-compose.yml` يوجد healthcheck للـdashboard والـdocs، ولا يظهر healthcheck تحت خدمة `bot` نفسها. لذلك قد لا تكشف حالة `/health` وحدها فقد اتصال Telegram بعد الإقلاع.

### C7 — P2: تجاوزات مالية وزمنية في عرض بيانات العامل
داخل `bot.ts` تُحوّل قيم Prisma المالية إلى `Number` وتجمعها في JavaScript لعرض البدلات والسلف والمسحوبات، ويؤخذ شهر الحساب من `new Date().toISOString()` (UTC). هذا قد ينتج تقريبًا عشريًا أو اختلاف شهر قرب بداية الشهر بتوقيت القاهرة. يلزم مقارنة هذه المسارات بقواعد Decimal/التوقيت الرسمية قبل الاعتماد عليها؛ لم أتحقق من وقوع خطأ مالي فعلي.

### C8 — P2: الترحيلات معرفة لكن CI لا يستخدمها
توجد تسع مهاجرات في `packages/database/prisma/migrations`، وmanifest يعرف `db:migrate`، لكن سير CI ينفذ `db:push --accept-data-loss`. هذا لا يثبت chain الترحيل في CI ولا يختبر الترقية من إصدار قاعدة سابق.

### C9 — P2: عداد health مضلل بنطاقين مختلفين
مصدر البوت فعلًا polling وHTTP صحة أصلي. README وADR-005 وسجل اختبار تاريخي يصفون Hono/Webhook. هذا تعارض توثيق واختبارات مصدره لا يعكس التصميم الجاري.

## نقاط إيجابية من القراءة
- هناك فصل ملموس إلى 3 تطبيقات و9 حزم و3 موديولات، مع contracts وmodule loader وبوابات تحقق عديدة.
- قاعدة PostgreSQL تستخدم Prisma adapter و`pg.Pool`، وتوجد migrations وخدمات النسخ الاحتياطي في المستودع.
- نقطة القصور ليست غياب البنية، بل عدم اتساق حدودها مع الادعاءات: bot entrypoint ما زال يحمل منطق مجال، وعقد runtime مفتوح، وTenant غير موحد.

## أولويات الفحص/المعالجة المقترحة
1. تثبيت قرار single-company أو multi-tenant قبل تغيير schema أو نسخ الكود.
2. رسم قائمة ملفات business-specific مقابل Telegram/core/database/admin reusable، ثم فحص اعتماديات كل مجموعة.
3. مراجعة tenant-scoped access في جميع repositories/auth، أو إزالة Tenant بشكل متسق إذا اعتمد نموذج شركة واحدة وبعد موافقة مستقلة.
4. ربط أمر bootstrap الحقيقي ودليل README/06، ثم جعل CI يختبر migrations لا `db:push` فقط.
5. تدقيق health/readiness، types/contracts، حساب المال والتوقيت، وقيم Compose الافتراضية.

التوصيات أعلاه غير منفذة. لا يوجد في هذا العمل أي تعديل على source.
