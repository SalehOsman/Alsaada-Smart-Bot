# Functional Database Schema and Module Auto-Discovery Implementation Plan

> **For implementation:** نفّذ المهام بالتتابع داخل جلسة واحدة، مع مراجعة نتيجة كل مرحلة قبل التالية. لا تفويض لوكلاء فرعيين؛ منهج العمل المعتمد هنا هو وكيل واحد.

**Goal:** جعل مخطط قاعدة البيانات الناتج يعكس الوظائف المنفذة حاليًا فقط، مع امتلاك الموديولات لمخططاتها ومهاجراتها، وتجميعها تلقائيًا في مدخل Prisma مركزي واحد.

**Architecture:** يكون لكل موديول عقد قاعدة بيانات يعلن ملفات مخططه ومهاجراته، وتستخدم آلية اكتشاف الموديولات الرسمية هذه العقود نفسها. يظل إعداد Prisma المشترك مركزيًا، بينما تُجمع ملفات الموديولات في مجلد مخطط مولّد واحد ومتعدد الملفات؛ وتُعامل الموديولات المثبتة في بناء الإصدار على أنها مصدر المخطط، لا مفاتيح تفعيل الميزات المؤقتة وقت التشغيل.

**Tech Stack:** Prisma ORM 7.10.0، PostgreSQL 16، TypeScript، pnpm، GitHub Actions وDocker.

---

## النطاق والقرارات

هذه خطة لإصلاح ملكية مخططات قاعدة البيانات وطريقة تجميعها، وهي مكملة لخطة العمل 110 الخاصة بتوحيد المشروع على شركة واحدة؛ لا تعيد فتح قرار تعدد الشركات ولا تنفذ ترحيل Tenant بذاتها. يظل PostgreSQL هو المحرك المستهدف بحسب إعدادات الحزم الحالية، ولا تفترض الخطة دعم SQLite.

المقصود بـ«الوظائف الحالية» هو ما يصل إليه تنفيذ فعلي في تدفقات Telegram أو لوحة الإدارة أو الخدمات والمستودعات والمهام الخلفية، بما فيها الوظائف التي ما زالت داخل `apps/bot-server` ولم تنتقل إلى موديول. لا يكفي وجود مجلد موديول أو نموذج في المخطط لإثبات أن الوظيفة مستخدمة. وتبقى نماذج البنية المشتركة فقط إذا أثبت التتبع البرمجي اعتماد التشغيل الحالي عليها.

يكون المخطط المركزي حاوية لإعدادات `generator` و`datasource` والنماذج المشتركة حقًا. تكون نماذج المجال ومهاجراته مملوكة للموديول الذي ينفذ وظيفتها. التجميع حتمي في مسار مولّد مثل `.generated/database/schema/`، ولا يُعد هذا الناتج مصدرًا يدويًا للتعديل.

لا يؤدي تعطيل ميزة أو موديول أثناء التشغيل إلى إسقاط جداول أو بيانات. قائمة المخطط تأتي من مجموعة الموديولات المضمّنة في بناء الإصدار؛ أما إزالة موديول من قاعدة إنتاج فتحتاج قرار إيقاف وترحيلًا صريحًا وخطة حفظ أو نقل بيانات.

## خط الأساس الذي يجب تأكيده قبل التنفيذ

- المصدر المركزي الحالي هو `packages/database/prisma/schema.prisma`، وفيه إعداد Prisma ونماذج قطاعات متعددة.
- `tools/modules/compose-database.ts` يبحث حاليًا عن مجلدات `modules/*/database` مباشرة، ويتعامل مع `schema.prisma` و`relations.contract.json`، ثم ينسخ المهاجرات إلى `.generated/database/migrations`. هذه آلية اكتشاف منفصلة عن `tools/modules/catalog.ts` ومحمل التشغيل.
- عقود `settings` و`workforce` لا تعلن حاليًا مساهمة قاعدة بيانات، بينما عقد `sandbox` يعلن ملفات مخطط وعلاقات. يجب فحص الملفات الموجودة فعليًا قبل تصنيف أي نموذج أو موديول.
- أوامر `db:generate` المعتادة في `packages/database/package.json` و`packages/database/prisma.config.ts` تستهدف المخطط المركزي، بينما أداة التركيب لها مسار مستقل. يجب أن ينتهي التنفيذ بمصدر إعداد واحد لجميع مسارات البناء والتوليد والترحيل.
- تقرير تقييم قاعدة البيانات في هذا المجلد يسجل وجود Tenant في لقطة الفحص، لكن قراءة `schema.prisma` التي بُنيت عليها هذه الخطة لا تعرض نموذج Tenant. لذلك يجب إعادة تثبيت لقطة الملفات والمهاجرات وحالة Git قبل إجراء أي قرار تنفيذي متعلق بـ Tenant؛ لا تفترض الخطة حالة قاعدة تشغيلية أو إنتاجية.
- يجب تقييم جودة الاختبارات القائمة في `تقييم-الاختبارات/` على حدة. نجاحها وحده لا يثبت صحة تصنيف النماذج أو أمان المهاجرات.

## الملفات والمسؤوليات المتوقعة

| المسار | مسؤولية التغيير عند اعتماد التنفيذ |
|---|---|
| `packages/database/prisma/schema.prisma` أو ملفات مجلد مخطط مركزي جديد | إعداد Prisma والنماذج المشتركة فقط |
| `modules/<module>/module.contract.json` | إعلان ملفات مخطط الموديول ومهاجراته واعتماداته |
| `modules/<module>/database/schema.prisma` | نماذج المجال التي يملكها الموديول |
| `modules/<module>/database/relations.contract.json` | علاقات عابرة للملكية مصرح بها ومتحقق منها، عند الحاجة فقط |
| `modules/<module>/database/migrations/<timestamp>_<name>/migration.sql` | ترحيلات الموديول المرتبطة بنماذجه |
| `tools/modules/catalog.ts` و`tools/modules/compose-database.ts` | استخدام سجل/عقود الاكتشاف الرسمية وإنتاج مخطط متعدد الملفات حتميًا |
| `tools/modules/validate-migrations.ts` و`tools/modules/deploy-migrations.ts` | التحقق والنشر من المصدر الموحد، أو إزالة المسار المتعارض بعد حسم محرك الترحيل |
| `packages/database/prisma.config.ts` و`packages/database/package.json` | توجيه Prisma إلى المخطط المجمّع في التوليد والترحيل |
| `.github/workflows/ci.yml` و`docker/Dockerfile` | تطبيق نفس عملية التركيب قبل توليد العميل والبناء والنشر |
| `docs/` و`docs/schemas/` | توثيق ملكية الجداول، عملية التوليد، وترحيل/إيقاف الموديول |

لا يُسمح للموديول بتعديل ملف مصدر موديول آخر ضمنيًا. إذا احتاج علاقة مع نموذج مشترك، يجب أن تكون العلاقة معلنة بعقد صريح ويتحقق المجمع من الطرفين، أسماء الحقول، المراجع، والتكرار قبل التوليد.

## مراحل التنفيذ

### المهمة 1: تثبيت خط الأساس وجرد استخدام النماذج

**الملفات:** قراءة `packages/database/prisma/schema.prisma`، ومستودعات `packages/database/src/`، ومصادر الخدمات والتدفقات في `apps/` و`modules/`، وسجل الموديولات وعقودها، وكل المهاجرات الحالية. لا تعديل لهذه الملفات في هذه المهمة.

- [ ] سجّل لقطة Git وتاريخها، ومخطط Prisma الفعلي، قائمة الموديولات والعقود، وقائمة مهاجرات PostgreSQL الحالية.
- [ ] تتبع لكل نموذج: مستهلك الخدمة/المستودع، مسار الاستخدام الذي يصل إليه، مالك المجال، والموديول الذي ينبغي أن يملكه. صنّف النتيجة: مشترك مستخدم، مجال مستخدم، غير مستخدم حاليًا، أو غير محسوم.
- [ ] ابحث عن مراجع كل نموذج في التطبيق والمهام وواجهات الإدارة وسكربتات التهيئة والبذر، لا في ملفات الاختبارات وحدها.
- [ ] افصل النماذج التي لا يقابلها تنفيذ حالي عن خطة الإزالة؛ لا تحذفها من مصدر المخطط قبل تحليل أثرها على قواعد البيانات والمهاجرات.
- [ ] أخرج سجلًا يمكن مراجعته يربط `model → repository/service → entry point/flow → owner`، واكتب الاستثناءات غير المحسومة صراحة.

**معيار الإكمال:** لكل نموذج قرار ملكية ودليل استخدام ساكن أو سبب موثق لبقائه مشتركًا؛ لا يبقى نموذج مجال مصنفًا «حاليًا» لمجرد وجوده في المخطط.

### المهمة 2: تعريف حدود الملكية وعقد مساهمة الموديول

**الملفات:** `modules/settings/module.contract.json`، `modules/workforce/module.contract.json`، `modules/sandbox/module.contract.json`، وأي عقد موديول إضافي يظهر في جرد مجلد `modules/`.

**ترحيل الموجود فعليًا إلى العقد الجديد:**

| الموديول الحالي | الحالة المقروءة في 2026-09-25 | الإجراء الإلزامي في التنفيذ |
|---|---|---|
| `settings` | عقد قديم نسبيًا بلا قسم `database`، ولا يوجد `modules/settings/database/` | تتبع تدفقات الإعدادات والمستودعات التي تستخدم نماذج Prisma، ثم إنشاء مخطط موديول ومهاجرات فقط للنماذج التي يملكها هذا المجال ويستخدمها التنفيذ. تحديد ما يبقى مشتركًا في الحاوية وما يخص `workforce` أو خدمات النواة قبل النقل. |
| `workforce` | عقد قديم نسبيًا بلا قسم `database`، ولا يوجد `modules/workforce/database/` | تتبع تدفقات العاملين والتسجيل والملفات والرواتب والإجازات والمطالبات وأي خدمات أخرى مثبتة فعليًا؛ إنشاء مخطط ومهاجرات مملوكة للموديول للنماذج الحالية التي تخصه، لا لكل النماذج التي تحمل اسم HR في المخطط. فحص استهلاك `bot-server` ولوحة الإدارة لهذه النماذج وتوافقها بعد النقل. |
| `sandbox` | عقد أحدث يعلن `schemaFile` و`relationsFile`؛ مجلد قاعدة بيانات موجود وفيه مخطط تعليقي تجريبي وعقد علاقات فارغ | تحويل إعلان العقد إلى الصيغة الموحدة. لا تعتبر `SandboxRecord` نموذجًا فعليًا ولا تضف جدولًا تجريبيًا للمخطط الناتج؛ إن لم يثبت وجود وظيفة حالية تتطلب قاعدة بيانات، يعلن العقد صراحة عدم وجود مساهمة DB أو يحذف قسم DB. تبقى وظيفة الموديول نفسها خارج نطاق التغيير ما لم تعتمد على نموذج غير موجود. |

- [ ] أعد جرد مجلد `modules/` عند بدء التنفيذ؛ هذه القائمة لقطة حالية وليست افتراضًا بأن عدد الموديولات سيظل ثابتًا. يجب أن ينتهي كل موديول موجود إلى حالة صريحة واحدة: مساهمة قاعدة بيانات معلنة وصحيحة، أو لا يملك مساهمة DB.
- [ ] قبل نقل أي نموذج، أنشئ جدول تتبع خاصًا بكل موديول: تدفق/نقطة دخول ← خدمة/مستودع ← استدعاء Prisma ← النموذج ← المالك المقترح. ضمّن الاستخدامات المباشرة داخل `apps/bot-server` وأي تطبيق آخر.
- [ ] ثبّت صيغة واحدة للعقد، مثل `database.schemaFiles` و`database.migrationsDir` ونسخة واجهة المخطط، بمسارات نسبية داخل الموديول.
- [ ] اعتبر غياب قسم `database` تصريحًا بأن الموديول لا يضيف جداول، وليس سببًا للبحث عن ملفات غير معلنة.
- [ ] أعلن صراحة كل مساهمة حقيقية من `settings` و`workforce` بدل إبقاء اعتمادها على `@alsaada/database` وحده؛ لا تضف مخططًا لـ`sandbox` ما لم ينتج الجرد نموذجًا مستخدمًا له.
- [ ] حدّد قواعد الملكية: الموديول يملك نماذج مجاله ومهاجراته؛ الحاوية تملك الكيانات المشتركة؛ التعديلات على كيانات موديول آخر ممنوعة إلا عبر واجهة علاقات معلنة ومتحقق منها.
- [ ] أضف تحققًا من مسارات العقود حتى لا يستطيع المسار النسبي الخروج من مجلد الموديول.

**معيار الإكمال:** يمكن معرفة مساهمة قاعدة البيانات كاملة من عقود الموديولات، ولا تعتمد على استنتاجها من أسماء المجلدات.

### المهمة 3: توحيد اكتشاف الموديولات وتركيب المخطط

**الملفات:** `tools/modules/catalog.ts`، `tools/modules/compose-database.ts`، و`tools/modules/tests/database-composition.spec.ts` مع اختبارات اكتشاف العقود ذات الصلة.

- [ ] اجعل المركّب يستهلك نفس سجل العقود/نتيجة الاكتشاف التي يستخدمها النظام، أو استخرج واجهة اكتشاف مشتركة يستخدمها الاثنان. أزل المسح المكرر المستقل داخل المركّب.
- [ ] اجمع إعدادات الحاوية وملفات Prisma التابعة للموديولات في مجلد واحد متعدد الملفات، مع أسماء وترتيب حتميّين، بدل دمج نصوص `schema.prisma` وحقن الحقول عبر مطابقة نصية.
- [ ] انقل إعداد `generator` و`datasource` إلى نقطة مركزية واحدة؛ يجب ألا يكررها أي جزء موديولي.
- [ ] ارفض تعارض نماذج/enums، العلاقات غير المكتملة، الملفات المعلنة المفقودة، المهاجرات ذات الاسم المكرر، الإصدارات غير المتوافقة، والاعتمادات على موديول غير مضمن. لا تتجاهل الأخطاء بصمت.
- [ ] لا تستخدم حالة تفعيل الميزة وقت التشغيل معيارًا لحذف المخطط. إذا كانت حزمة إصدار تستبعد موديولًا، يجب أن يكون الاستبعاد قرار بناء صريحًا وقابلًا للتكرار.
- [ ] اكتب manifest أو بصمة تجميع تشمل هوية الموديولات ونسخها وملفات المخطط والمهاجرات، لتسهيل مراجعة سبب اختلاف الناتج بين بنائين.

**معيار الإكمال:** بناءان من المدخلات نفسها ينتجان بنية وبصمة متطابقتين، ويؤدي أي عقد غير صالح أو علاقة مفقودة إلى فشل مبكر واضح.

### المهمة 4: نقل النماذج إلى مالكيها تدريجيًا

**الملفات:** المخطط المركزي ومخططات الموديولات التي حددتها خريطة المهمة 1، مع عقود العلاقات والمهاجرات التابعة لها.

- [ ] ابدأ بترحيل `settings` و`workforce` وفق جدول المهمة 2: أنشئ مجلدات DB وعقود مساهمة فقط بعد إثبات ملكية النماذج، وانقل تدريجيًا النماذج المستخدمة حاليًا إلى ملفات الموديول. لا تتركهما يعتمدان ضمنيًا على وجود كل نماذج المجالات في المخطط المركزي.
- [ ] عالج `sandbox` كحالة بلا نموذج DB فعلي ما لم يثبت العكس من شيفرة وظيفية حالية؛ لا تُدخل النموذج التعليقي أو عقد العلاقات الفارغ في ناتج Prisma.
- [ ] حافظ على واجهة Prisma التي تستهلكها تدفقات الموديولات أثناء نقل مكان تعريف النموذج: يجب أن يبقى العميل المجمّع يولّد النماذج التي يحتاجها التطبيق، أو تُحدّث جميع المستهلكات في التغيير نفسه عند وجود إعادة تسمية مبررة.
- [ ] ابدأ بنموذج أو مجموعة مترابطة واحدة في كل تغيير، وحافظ على أسماء الجداول والأعمدة والقيود القائمة ما لم توجد مهاجرة تحويل منفصلة ومراجعة.
- [ ] أبقِ النماذج المشتركة في الحاوية فقط عندما يستهلكها أكثر من مجال أو بنية تشغيلية مشتركة مثبتة.
- [ ] انقل نماذج المجالات المنفذة إلى موديولها، حتى إن كانت نقطة الدخول الحالية داخل `apps/bot-server`؛ انقل الملكية بحسب المجال الفعلي لا مكان الملف التاريخي فقط.
- [ ] لا تترك تعريف النموذج في المخطط المركزي ونسخة ثانية في موديول. يجب أن يكشف التحقق أي ازدواجية.
- [ ] لا تسقط نموذجًا غير مستخدم ضمن هذه الخطوة تلقائيًا؛ اجمع المرشحين للإزالة في تغيير ترحيل مستقل بعد إثبات عدم وجود مستهلك أو بيانات مطلوبة.

**معيار الإكمال:** لا يحتوي المخطط المركزي على جداول مجال مملوكة للموديولات، ولا توجد نماذج مجال حية بلا مالك معلن.

### المهمة 5: جعل المهاجرات ذات تاريخ واحد وسلوك آمن

**الملفات:** `tools/modules/validate-migrations.ts`، `tools/modules/deploy-migrations.ts`، `packages/database/prisma/migrations/`، `modules/*/database/migrations/`، و`packages/database/prisma.config.ts`.

- [ ] احصر تاريخ المهاجرات الحالي وسجل التطبيقات الموجود في البيئات، وقارن ناتج المخطط مع ما تنشئه المهاجرات؛ لا تعدّل مهاجرة سبق نشرها.
- [ ] احسم واعتمد محركًا واحدًا مرجعيًا لإدارة سجل التطبيق. لا تخلط Prisma Migrate و`_module_migrations_applied` و`db push` باعتبارها مصادر متساوية للحقيقة.
- [ ] إذا بقي المجمع المخصص، اجعله يرفض غياب مجلد مهاجرات إلزامي في النشر بدل اعتبار غياب المجلد نجاحًا بصفر مهاجرات. وإذا اعتمد Prisma Migrate، وجّه الأوامر كلها إلى مجلد المخطط والمهاجرات المجمّع نفسه.
- [ ] افحص ترتيب المهاجرات، الأسماء الفريدة، إعادة التشغيل، المعاملات، الأقفال، وفشل الترحيل والاستعادة. لا تنفذ إسقاط جداول عند اختفاء موديول من ملف بناء.
- [ ] لأي نموذج أو عمود ستتم إزالته، اكتب مهاجرة تحفظ أو تنقل البيانات عند الحاجة، وحدد النسخة الاحتياطية وخطوات الاستعادة ونافذة التوقف، ثم نفذ تجربة على قاعدة مؤقتة مطابقة للبيئة المستهدفة قبل الإنتاج.

**معيار الإكمال:** مخطط نظيف يمكن بناؤه من التاريخ المعتمد، والانتقال لا يعتمد على `db push --accept-data-loss`، ولا تتحول إزالة موديول إلى حذف بيانات ضمني.

### المهمة 6: توحيد التوليد والبناء والنشر

**الملفات:** `packages/database/package.json`، `packages/database/prisma.config.ts`، `.github/workflows/ci.yml`، `docker/Dockerfile`، وأوامر النشر في `tools/modules/cli.ts` و`tools/modules/deploy-migrations.ts` عند انطباقها.

- [ ] أضف خطوة تركيب واحدة معلومة الترتيب قبل `prisma generate` في التطوير وCI وDocker؛ لا تسمح بتوليد العميل من `packages/database/prisma/schema.prisma` بينما التشغيل يستخدم مخططًا مجمعًا آخر.
- [ ] وجه أوامر Prisma عبر إعداد واحد إلى `.generated/database/schema/` ومجلد مهاجراته المطابق، وتحقق من مسارات العمل النسبية داخل CI وDocker.
- [ ] اجعل عميل Prisma المولّد الذي تستهلكه الحزم هو نفسه المبني من المخطط الناتج، وأزل أي نسخ/توليد قديم يشير إلى مخطط بديل.
- [ ] استبدل دفع المخطط غير القابل للتتبع في CI بمسار تطبيق المهاجرات المعتمد بعد إثباته على قاعدة مؤقتة فارغة وعلى ترقية قاعدة تحمل المخطط السابق.
- [ ] اجعل أوامر الإصدار ترفض بصمة غير متوافقة بين العميل والمخطط والمهاجرات.

**معيار الإكمال:** كل المسارات الرسمية للتوليد والبناء والنشر تشير إلى مصدر وترتيب واحدين، وتفشل إذا لم يكتمل التجميع.

### المهمة 7: توثيق قواعد التشغيل والتقاعد

**الملفات:** الوثائق ذات الصلة في `docs/` و`docs/schemas/`، وملفات README الخاصة بالموديولات عند وجودها.

- [ ] وثّق أين يضع المطور مخطط الموديول، وكيف يعلنه في العقد، وكيف يطلب علاقة مشتركة، وكيف ينشئ مهاجرة.
- [ ] وثّق أن ملف Prisma المركزي حاوية، وأن `.generated/database/schema/` ناتج آلي لا يُعدل يدويًا.
- [ ] وثّق الفرق بين اكتشاف الموديول في المستودع، تضمينه في بناء الإصدار، تفعيله أثناء التشغيل، وإزالته مع حفظ البيانات.
- [ ] صحح الوثائق التي تصف tenancy أو خيارات SQLite/PostgreSQL بحسب قرار المنتج والملفات الفعلية بعد إعادة التحقق؛ لا تنقل وصفًا قديمًا إلى الخطة الجديدة كحقيقة.
- [ ] أضف مسار الخطة إلى فهرس تقييم 2026-09-25، واربط نتائج التنفيذ لاحقًا بالملفات والمهاجرات الفعلية بدل تحويل التوصيات إلى ادعاء تنفيذ.

**معيار الإكمال:** يستطيع مطور جديد إضافة موديول بلا تعديل يدوي غير معلن للمخطط المركزي، وتصف الوثائق دورة حياة الجداول بوضوح.

### المهمة 8: التحقق من الناتج بعد التنفيذ

**التحقق الساكن:** راجع كل نموذج وعلاقة وعقدة ومهاجرة في الناتج المجمّع، وقارن البصمة وقائمة الموديولات مع manifest الإصدار. راجع ألا يعتمد نموذج مجال مستبعد على مستهلك ما زال داخل التطبيق.

**التحقق البنيوي:** شغّل formatter وvalidator وعميل Prisma generation على المجلد المجمّع. طبّق تاريخ المهاجرات على قاعدة PostgreSQL مؤقتة فارغة، ثم على نسخة مستنسخة من المخطط السابق، وقارن القيود والجداول الناتجة بالمخطط المتوقع.

**الاختبارات:** قيّم تغطية واختبارات تركيب العقود، الحتمية، العلاقات، وترقية المهاجرات في مجلد تقييم الاختبارات بصورة منفصلة. بعد إصلاح الاختبارات ذات الصلة شغّلها كدليل مساعد للتغيير، لا كبديل عن مراجعة الملفات أو مقارنة المخطط والمهاجرات. لا يثبت نجاح مجموعة الاختبارات سلامة قاعدة الإنتاج.

**معايير القبول النهائية:**

- [ ] كل نموذج في المخطط المجمّع يخدم وظيفة حالية موثقة أو قدرة مشتركة مستخدمة ومبررة.
- [ ] لكل نموذج مجال مالك موديول معلن؛ ولا توجد نماذج مستقبلية غير مستخدمة ضمن مخطط الإصدار بلا مبرر.
- [ ] الملف المركزي يملك إعداد Prisma والكيانات المشتركة فقط، وملفات الموديولات تكتشف من عقود الاكتشاف الرسمية.
- [ ] توليد العميل وCI وDocker والتطبيق والنشر يستخدمون التجميع نفسه.
- [ ] لا ينتج عن تعطيل ميزة أو غياب مجلد مهاجرات حذف بيانات أو نجاح نشر زائف.
- [ ] حالة Tenant ومهاجراته محسومة بعد مقارنة لقطة المصدر وتاريخ المهاجرات وقواعد البيانات المتاحة، دون افتراض حالة إنتاج غير مفحوصة.
- [ ] الوثائق وسجل ملكية البيانات متطابقان مع الملفات بعد التنفيذ، وتظل مراجعة جودة الاختبارات مسجلة في مجلد تقييمها.

## المخاطر وحدود الخطة

- نقل النماذج قد يغير تاريخ المهاجرات أو يفصل علاقات عابرة للمجالات؛ لا تنفذ نقلًا جماعيًا بلا خريطة اعتماد ومقارنة SQL.
- وجود موديول في الشيفرة لا يعني بالضرورة أنه جزء من المنتج المنشور؛ يجب تثبيت سياسة مجموعة بناء الإصدار قبل الاعتماد على الاكتشاف الآلي.
- الملفات لا تثبت حالة قاعدة البيانات الحية أو المهاجرات المطبقة فعليًا. يلزم جرد معتمد ونسخ احتياطي وتجربة ترقية قبل أي خطوة مدمرة.
- الخطة لا تُجيز تعديلات تلقائية على ملفات المصدر أو تنفيذ ترحيل في الإنتاج. كل مرحلة تنفيذية تحتاج مراجعة تغييراتها ضمن سير العمل المعتمد للمشروع.
