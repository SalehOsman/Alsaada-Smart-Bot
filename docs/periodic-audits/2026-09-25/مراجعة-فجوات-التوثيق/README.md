# مراجعة فجوات التوثيق الحالية — 2026-09-25

## الحكم
التوثيق واسع، لكنه لا يعطي صورة واحدة موثوقة عن النظام الجاري. بعض النصوص التأسيسية تصف هدفًا متعدد الشركات وتخزين SQLite، بينما المصدر الحالي PostgreSQL وتشغيل شركة واحدة عمليًا. وثيقة خطة العمل 110 تصف هذا التعارض وتطلب مواءمته، لكنها موسومة **بانتظار اعتماد المالك**؛ لذلك لا ينبغي التعامل مع المقترح على أنه مطبق. README والفهارس وقرارات ADR ما زالت تصف واقعًا مختلفًا.

هذا تقرير مطابقة ساكنة بين نصوص مختارة في README و`docs/` وبوابة الوثائق وخطط العمل وبين ملفات المصدر والإعدادات. لا يشمل تدقيق حقيقة جميع الـ126 وظيفة مقابل المشروع القديم، ولا تحققًا تشغيليًا أو مراجعة لكل صفحة من 1,707 ملفات Markdown.

## النتائج

### D1 — P1: نموذج المنتج غير محسوم في الوثائق التأسيسية
- `README.md` (الأسطر 30–32) يسوق **White-Label Multi-Tenant Engine** لأي شركة.
- `docs/00-baseline-and-ssot-charter.md` يرسم جاهزية White-Label Multi-Tenant.
- `docs/06-tenant-onboarding-and-provisioning-wizard.md` يشرح مئات الشركات، `tenant.config.ts` وعزلًا تامًا، ويدعم SQLite أو PostgreSQL.
- المصدر يملك Tenant/tenantId جزئيًا لكنه لا يحمل tenant identity في ModuleRuntimeContext ولا يفرضه في كل المستودعات. خطة `110` تسمي هذه الفجوة وتخطط لحذف النموذج، لكنها **Pending Sovereign Approval**.

الأثر: لا يعرف المطور هل عليه إضافة عزل حقيقي أم الاستمرار في شركة مفردة وإزالة مفاهيم التعدد. لا تصف الوثائق الحالية المنتج الجاري بصورة دقيقة.

### D2 — P1: تعليمات التشغيل تستدعي وظائف غير موجودة وتخزن خيارات غير مدعومة
- `docs/06` وREADME يذكران `npm run system:provision` و`npm run tenant:init`؛ الجذر يعرّف `system:provision` إلى `tsx scripts/provision.ts` لكن `scripts/provision.ts` غير موجود، و`tenant:init` لا يظهر كسكربت.
- الحزمة تعرف بدلًا من ذلك `db:migrate` و`db:seed:company`.
- `docs/06` يقدم SQLite كخيار؛ طبقة DB تستعمل Prisma adapter للـPostgreSQL و`pg.Pool`.
- README يذكر Hono Webhook؛ مداخل التشغيل الحالية تستعمل grammY runner و`node:http` لنقطة الصحة.

الأثر: خطوات الإعداد للمطور/المشغل قد تفشل أو تختار بنية لا يدعمها التنفيذ.

### D3 — P1: قرارات معمارية منشورة كـAccepted أصبحت مخالفة للواقع
`tools/docs/transform-pipeline.ts` يثبت ADR-005 بوصف Hono API & Webhooks كقرار `Accepted`؛ والبوابة تعرضه كذلك. كما تعلن ADR-003 قاعدة Zero `any`، بينما عقود التشغيل بها `any` صريح. ينبغي أن يميز سجل ADR بين قرار نافذ وقرار مستبدل/ملغى، مع رابط للتنفيذ الحالي.

### D4 — P1: فهرس الوثائق الرسمي يحتوي رابطًا مكسورًا وتصادم ترقيم
- `docs/README.md` يعرض وثيقة الاختبارات باسم `28-master-tests-physical-reality-and-compliance-ledger.md`، وهذا المسار غير موجود؛ الملف على القرص هو `29-master-tests-physical-reality-and-compliance-ledger.md`.
- الفهرس يكرر الرقم 28 ويصف قسمه بأنه 00–28، مع أن README الرئيسي يربط الاختبارات بالرقم 29.
- `docs/README.md` يصف في الأعلى 235 ملف اختبارًا، وسجل `docs/29` يعلن 235/235 مطابقة 100%؛ الجرد الساكن بتاريخ هذا التقرير وجد 291 ملف `*.spec.ts`. هذا لا يقول شيئًا عن نجاح تشغيلها، لكنه يثبت أن أرقام/ادعاءات السجل قديمة وغير صالحة كجرد حالي.

### D5 — P1: شجرة README لا تمثل monorepo الحالي
README يرسم تطبيقًا واحدًا (`bot-server`) وأربع حزم وموديولين، بينما المجلدات الحالية تعرض 3 تطبيقات (`bot-server`, `admin-dashboard`, `docs`) و9 حزم و3 موديولات. هذا يقلل من دقة التعريف بنطاق المشروع ويخفي أجزاء تشغيلية رئيسية عن المطور الجديد.
### D5 — P2: سجل التقارير لا يتبع أحدث حالة
فهرس `docs/README.md` يذكر آخر مراجعات حتى 19 سبتمبر 2026، ولا يفهرس تقرير 23 سبتمبر أو تقرير 25 سبتمبر الجاري. README الجذر أيضًا يعرض مجموعة مختارة أقدم. هذا يضعف الوصول إلى الحكم الأحدث ويترك تقريرًا تاريخيًا يبدو مرجعًا حاليًا.

### D6 — P2: الترقيم المرجعي لخطط العمل غير فريد
وجدت أرقامًا مكررة لكل من 42 و47 و56 و57 و94 و101 في أسماء ملفات `docs/work-plans`. أي إحالة إلى “الخطة 101” مثلًا لا تحدد مستندًا واحدًا. خطة 91 نفسها تذكر معالجة اصطدامات الترقيم؛ الاصطدامات أعلاه باقية في الشجرة الحالية.

### D7 — P2: مقياس حجم المكتبة يخفي صعوبة اكتشاف المعرفة
يوجد 1,707 ملف Markdown تحت `docs/`؛ منها 1,473 ملفًا في `docs/ai-execution-evidence` و117 خطة عمل، مقابل 70 صفحة في محتوى بوابة docs. هذه الأعداد ليست خللًا بحد ذاتها، لكنها تعني أن رقم “حجم التوثيق” يهيمن عليه دليل التنفيذ المتكرر/المؤرخ لا الأدلة التشغيلية للمستخدم. يحتاج الفهرس إلى فصل واضح بين: دليل التشغيل الحالي، المعايير الحاكمة، السجل التاريخي، والخطط المعلقة.

### D8 — P2: السجل يخلط المتطلبات والواقع وأدلة تحقق تاريخية
تتضمن الوثائق صيغًا قطعية مثل “مطابقة 100%” أو مخرجات تهيئة مكتملة، فيما خطط العمل اللاحقة تصف غياب ملفات أو اختلاف الواقع وتبقى بانتظار اعتماد. الخطة 110 تعترف بالفجوات نفسها وتضعها ضمن عمل مستقبلي. لا يوجد في كل موضع تاريخ تحقق/commit/بيئة يبين هل العبارة متطلب تصميم أو تنفيذ قائم أو نتيجة تاريخية.

## توصيات توثيقية
1. اعتماد وثيقة حالة قصيرة تحدد: شركة مفردة أم تعدد شركات، PostgreSQL فقط أم غيره، polling أم webhook، وما هو داخل المنتج اليوم وما هو مخطط.
2. توحيد README و`docs/00` و`docs/06` وADR وسجل الموديولات حول هذه الحالة بعد حسمها؛ إبقاء خطة 110 كمقترح إلى حين اعتمادها لا كحقيقة منفذة.
3. إصلاح أسماء/أرقام الفهارس، وإضافة فحص ساكن للروابط والفهارس كجزء من التحقق، دون استنتاج نجاح من وجود الأمر فقط.
4. ترقيم خطط العمل بمعرف فريد لا يعاد استخدامه، وتسجيل الحالة والفرع وآخر تحديث والنتيجة بوضوح.
5. إضافة metadata لكل تقرير: تاريخ، commit، نطاق، نوع الفحص (ساكن/تشغيلي)، وحدود الثقة. تمييز ما هو Requirement عن Evidence وعن Remediation Plan.
6. تقليل عبارات `100%` إلى ادعاءات لها معيار قابل للتفسير ودليل محدد ومؤرخ.
