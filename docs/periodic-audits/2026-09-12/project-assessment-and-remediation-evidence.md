## الملخص التنفيذي

المشروع يملك أساساً معمارياً جيداً: Mono-repo واضح، Prisma، Redis، PostgreSQL، حدود موديولات، وحزمة @alsaada/telemetry وحلقة ErrorVaultService. لكنه **ليس جاهزاً للإطلاق أو للاعتماد على لوحة التحكم** في حالته الراهنة. السبب ليس نقص واجهات فقط؛ بل توجد فجوة اتساق بين مخطط Prisma وقاعدة البيانات الفعلية، وسجل توثيق يعلن اكتمال تغييرات غير متتبعة في Git، وفحوص جذرية تفشل بينما يعطي البناء الأخضر انطباعاً مضللاً.

## السبب الجذري المثبت لتعطل الدخول للوحة التحكم

1. الحزمة packages/database/prisma/schema.prisma عرّفت AuditLog.traceId وSystemErrorLog.traceId وSystemErrorLog.service.
2. مجلد Prisma يحتوي فقط الهجرة 20260911000000_init_enterprise_hash_ledger، ولا تضيف هذه الأعمدة.
3. المسار apps/admin-dashboard/src/app/api/auth/magic/route.ts ينفذ prisma.auditLog.findFirst قبل إصدار cookie الجلسة.
4. Prisma يستعلم نموذج AuditLog كاملاً، فيطلب العمود audit_logs.traceId غير الموجود ويعيد P2022.
5. لا توجد معالجة لهذا الاستعلام المبكر؛ لذلك يفشل الرابط السحري قبل إنشاء alsaada_session.

**النتيجة:** خلل المصادقة ليس خطأ HMAC مبدئياً؛ هو انحراف Schema/Migration يوقف الطريق قبل الجلسة. نجاح اختبارات HMAC لا ينفيه لأنها لا تبدأ من قاعدة بيانات مهيأة بالمهاجرات الحقيقية.

### عيوب مصادقة مرافقة

- حارس منع إعادة الاستخدام يستعلم ثم يكتب في AuditLog؛ لا يضمن التفرد بين عدة نسخ من الخدمة. يلزم جدول claim فريد للـJTI داخل transaction.
- فشل كتابة أثر التدقيق يُبتلع حالياً بعد حجز الذاكرة؛ هذا لا يحقق fail-closed ولا يعطي رسالة تشغيلية سليمة.
- لا توجد readiness check تمنع dashboard من الخدمة إذا كانت prisma migrate status أو الجداول الأساسية غير متوافقة.
- إصدار رابط Telegram Mini App على HTTP محلي يرفضه Telegram؛ يجب ألا يظهر زر Web App إلا مع URL يبدأ بـ HTTPS، مع مسار متصفح بديل واختبار يحاكي رفض Telegram.

## تقييم منظومة تسجيل الأخطاء الحالية — 40%

### ما هو موجود ومفيد

- packages/telemetry ينتج سجلات JSON ويحتوي Redaction وContext وAdapters لـ Next وGrammy.
- ErrorVaultService يحفظ حوادث البوت في SystemErrorLog، يستنتج خطورة، يجمع breadcrumbs، ويعطي المستخدم رمز بلاغ.
- توجد واجهات أخطاء Next وواجهة مراجعة أخطاء داخل dashboard.
- يوجد تنبيه Telegram للسوبر أدمن وDeduplication بدائي لكل ساعة.

### ما يمنع اعتبارها احترافية أو كافية

| الفجوة | الدليل | الخطر |
|---|---|---|
| عدم استمرارية التخزين | Error Vault يكتب حقولاً غير موجودة في قاعدة البيانات. | حادثة البوت قد تفشل في التخزين في نفس الظرف الذي نحتاج فيه السجل. |
| تسرب محتمل للبيانات | ErrorVaultService يحفظ error.message وstack مباشرة ولا يستدعي redact. | تسرب توكنات أو رقم قومي أو بيانات طلب في السجل والتنبيه. |
| أخطاء الواجهة غير موحدة | Error Boundaries ومسارات API تستخدم console.error. | لا يوجد Incident أو تنبيه أو Trace موثوق لخطأ dashboard. |
| Trace غير موحد | Adapter Grammy موجود لكنه غير مستخدم من البوت الفعلي. | لا يمكن ربط /dashboard بالرابط السحري ثم صفحة الإدارة. |
| ابتلاع الأخطاء | توجد عدة catch صامتة في مسار التنبيه والرد. | تتحول مشكلة التسليم أو التخزين إلى صمت تشغيلي. |
| لا توجد دورة حادث | الحقول تنتهي عملياً عند isResolved. | لا مالك، تأكيد استلام، SLA، سبب علاج، أو إعادة فتح. |
| التنبيه مباشر داخل مسار الفشل | إرسال Telegram ينتظر داخل المعالجة. | يزيد زمن الخطأ ويضاعف الضرر عند تعذر Telegram. |
| لا توجد مراقبة للبنية | لا توجد مقاييس وtraces وalert rules موحدة. | لا يمكن تمييز أعطال PostgreSQL/Redis/Docker عن خطأ تطبيق. |

## قرار المعمارية المعتمد

لا يُعتمد Sentry ولا GlitchTip كمرجع الحقيقة. المرجع سيكون **Incident Vault داخلياً في PostgreSQL** مع تنبيهات عبر طابور موثوق، وtraceId موحد. تعتمد الخدمات معيار **OpenTelemetry** وتُرسل إلى Collector داخلي؛ ويكون Grafana Loki + Tempo هو المسار الافتراضي للمراقبة الذاتية. يمكن اختيار SigNoz بدلاً من Loki + Tempo لاحقاً، بعد قياس السعة والتكلفة التشغيلية، لا بالتوازي معها.

## بوابة الإصدار

يحظر إطلاق dashboard أو تحديث حالة NEW-52 إلى NEW-59 إلى «مكتمل» قبل تحقق جميع الشروط التالية:

1. نسخة احتياطية موثقة لقاعدة البيانات، ثم تطبيق migration عبر عملية محكومة.
2. أمر prisma migrate status يعرض أن قاعدة البيانات متزامنة باستخدام DATABASE_URL صريح.
3. اختبار رابط سحري حقيقي ضد PostgreSQL مهيأ بالمهاجرات يثبت cookie وanti-replay ورفض DB الآمن.
4. pnpm lint وpnpm test وpnpm governance:verify وpnpm build جميعها Exit 0.
5. اختبار Docker نظيف للصورتين وحاوية dashboard healthy.
6. اختبار Incident: خطأ بوت وخطأ Next يؤديان إلى سجل sanitized واحد قابل للبحث بالـtraceId وتنبيه queued.
7. شجرة Git نظيفة، وكل الملفات التي تدعي الوثائق وجودها متتبعة.
